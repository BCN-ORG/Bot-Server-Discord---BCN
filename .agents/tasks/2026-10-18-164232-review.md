# Payroll system implementation

The payroll system adds automatic weekly salary distribution for Discord members with eligible roles. The implementation handles coefficient summing, deduplication, API retries, and comprehensive history tracking. Four admin commands configure the system: salary coefficients, eligible roles, schedule, and manual payout.

**Watch for:** duplicate:true saved as distinct DUPLICATE status rather than SUCCESS (confirmed), empty eligible roles schedules cron job that wakes weekly with no work (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The scheduler cron expression matches the config correctly and restarts when schedule is updated. Coefficient calculation sums all eligible roles a user has and caps at 100, matching the spec. User deduplication works via Map keyed by member ID. The API client retry logic handles 409/503 with exponential backoff (2s, 4s, 8s) across 3 attempts. History records capture all required fields including eligibleRoles array, paidWithRole object, and allRolesAtTime snapshot. All four commands guard with PermissionFlagsBits.Administrator. Commands register correctly in discord.js and initPayrollScheduler is called in index.js after MongoDB connects. Import paths include .js extensions throughout.

The duplicate:true response from the API increments skippedCount but saves history with status=DUPLICATE, not SUCCESS. This contradicts the spec requirement that "duplicate:true treated as success/skip". Empty eligible roles returns early with zero counts, but scheduler initialization schedules a cron job that wakes weekly and logs "No eligible roles configured" without processing anyone—harmless but wasteful until an admin adds roles.

## duplicate:true treated as distinct status, not success

The spec states "duplicate:true treated as success/skip (not error)". The implementation saves history with `status: 'DUPLICATE'` and increments `skippedCount`, which is reasonable for reporting but diverges from treating it as success. The API response `duplicate: true` with `status: 'SUCCESS'` enters the branch that checks `transferResult.data?.duplicate === true` and sets `historyRecord.status = 'DUPLICATE'`. If the intent is to treat duplicate as a successful no-op, the history status should be 'SUCCESS' with a separate `duplicate` flag in the history record. If duplicate is meant to be distinct, the current approach is correct but the spec should clarify.

From payrollService.js lines 153-161:

```javascript
if (transferResult.data?.status === 'SUCCESS') {
  if (transferResult.data?.duplicate === true) {
    historyRecord.status = 'DUPLICATE';
    console.log(`[Payroll] ${member.user.tag}: Already paid this period`);
    skippedCount++;
  } else {
    historyRecord.status = 'SUCCESS';
    console.log(`[Payroll] ${member.user.tag}: Paid ${salaryInfo.amount} coins`);
    successCount++;
  }
}
```

## Empty eligible roles during scheduler init

When no roles have been added yet, `getAllEligibleRoles()` returns an empty array. The `initPayrollScheduler` function in scheduler.js does not check this condition—it proceeds to schedule the cron job. When the job fires, `processWeeklyPayroll` will return early with all counts at zero after logging "No eligible roles configured". This is not a bug (the scheduler works), but it means the cron job wakes weekly and does nothing until an admin adds roles via `/salary-roles add`. A startup warning would help admins understand the system is waiting for configuration.
